# Project context: Hybrid MPI + OpenMP image convolution

Read this file at the start of every task. It is the standing context for all phases.

## Who and what

Semester project for "Parallel and Distributed Computing" at NUCES (FAST) Karachi, section BCS-7B. It is graded on working code, measured performance, a written report and a viva where the student must be able to explain every part of the code.

Problem: apply convolution filters (Sobel edge detection, Gaussian blur, sharpening; kernel sizes 3x3, 5x5, 7x7) to a very large 8-bit grayscale image, then parallelise:

- OpenMP: threads share the rows of one process.
- MPI: the image is split into row-blocks across processes. Neighbouring ranks exchange halo (ghost) rows, with width = kernel radius, so pixels at block edges are correct. Rank 0 gathers the result.
- Hybrid: MPI ranks, each running several OpenMP threads.

Goal: a correct hybrid implementation and a rigorous performance study: execution time, speedup = T_sequential / T_parallel, efficiency = speedup / (processes x threads), across process and thread counts, with graphs, analysis and a final report.

## Contract: docs/DECISIONS.md (do not change without asking)

- Correlation (kernel not flipped); clamp-to-edge borders (final decision).
- float32 arithmetic in C; output = clamp(floor(x + 0.5), 0, 255).
- Sobel output = sqrt(gx^2 + gy^2).
- Image format everywhere: 8-bit grayscale binary PGM (P5).
- Kernels are defined in src/kernels.h and mirrored by the NumPy reference scripts/refconv.py.

## Correctness rules

- C sequential vs data/test/ref/: scripts/compare_images.py --tol 1.
- Every parallel version (OpenMP, MPI, hybrid) vs the C sequential output: bit-exact, --tol 0. A difference is a bug, usually at a block boundary or halo. Never loosen the tolerance to hide it.
- The test set includes awkward sizes on purpose: 101x77 (not divisible by process counts) and 5x5 (smaller than the 7x7 kernel). Also test thread/process counts larger than the number of rows.

## Dataset (decision: least work)

Only Dataset A: one synthetic 20000x20000 grayscale PGM (400 MB) at data/large/big_20000.pgm, generated by python3 scripts/gen_dataset.py --size 20000 --out data/large/big_20000.pgm. The batch dataset (B) was dropped on purpose. Do not generate or implement batch mode.

## Reduced Scope for Phases 3-5

- **Phase 3 (NEXT): MPI**
  - 1-D row blocks only.
  - Rank 0 reads the image and distributes with `MPI_Scatterv`.
  - Each rank exchanges `radius` halo rows with its upper and lower neighbours using blocking `MPI_Sendrecv`.
  - Clamp-to-edge at global top and bottom boundaries.
  - `MPI_Gatherv` back to rank 0, which writes output.
  - If a rank has fewer rows than the kernel radius, use fewer active ranks; idle ranks join collectives with 0 rows.
  - Bit-exact output (`--tol 0`) for 1, 2, 3, 4, 7, 12 processes across all test images (including 5x5 and 101x77).
- **Phase 4: Hybrid**
  - Same program with OpenMP threads inside each rank (`MPI_Init_thread` with `MPI_THREAD_FUNNELED`).
  - Thread count passed as argument; pure MPI is the 1-thread case.
- **Phase 5: Reduced Benchmark & Report**
  - Main config: Gaussian 5x5.
  - MPI-only: 1, 2, 4, 6, 12 processes (3 repeats).
  - OpenMP-only: reuse Phase 2b data.
  - Hybrid with 12 total threads: 2x6, 3x4, 4x3, 6x2 (3 repeats).
  - Kernel-size comparison: all 9 filter/size combinations at ONE setting only.
  - Four graphs: speedup, efficiency, hybrid comparison, kernel-size effect. Report and viva notes.
- **OUT OF SCOPE (do not build):**
  - Non-blocking communication/overlap, MPI parallel I/O, 2D domain decomposition/tiling, memory optimisation, multi-node runs, further schedule tuning, batch mode.
